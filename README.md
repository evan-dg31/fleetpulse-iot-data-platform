# FleetPulse — Fleet Telematics Streaming Platform

Portfolio starter: Geotab **demo** telemetry -> Kafka -> Azure Databricks Spark -> Delta Lake -> AI/BI dashboard.

FleetPulse is an end-to-end data engineering project for ingesting fleet GPS telemetry, processing events with Kafka and Spark Structured Streaming, maintaining historical time series and current device state in Delta Lake, and serving fleet monitoring metrics to a Databricks AI/BI dashboard.

Project goal: Enable fleet operators to answer: Where is equipment? Which assets are moving or stationary? How fresh are the readings? Diagnostics, engine-hours-based utilization, and maintenance insights are future extensions and require additional source data

## Solution architecture

```text
Phase 1 (core):
Geotab demo fleet (simulated records)
  -> Geotab GetFeed (incremental REST polling)
  -> Python ingestion service (uv-managed)
  -> Apache Kafka [fleetpulse.gps.raw]
  -> Databricks Spark Structured Streaming
  -> Bronze Delta -> Silver Delta -> Gold device state
  -> Databricks AI/BI Dashboard

Phase 2 (planned, separate source):
Simulated IoT devices -> MQTT broker -> Kafka -> canonical pipeline
```

**Why no MQTT in Phase 1?** Geotab already manages communication with connected devices. The Geotab integration uses its cloud API. MQTT is useful when building a separate direct-device ingestion path, not as an artificial hop between Geotab and Kafka.

## Step 1. Set up Local development using uv (VS Code / PowerShell)

**Prerequisites:** [uv](https://docs.astral.sh/uv/getting-started/installation/), [VS Code](https://code.visualstudio.com/), Docker Desktop, and Git. Azure Databricks and a Geotab demo account are only needed for later stages.

Install uv (one option on Windows):

```powershell
winget install --id astral-sh.uv -e
uv --version
```

Open this project directory in VS Code, then in the integrated PowerShell terminal run:

```powershell
# Run from the folder containing pyproject.toml
uv sync
Copy-Item .env.example .env
uv run pytest -q
```

`uv sync` installs the Python version and dependencies needed for the project, creates `.venv`, and generates `uv.lock` if it does not exist. `uv run` uses that environment automatically, so you **do not need** `python -m venv`, `pip install`, or manual activation.

In VS Code, choose **Python: Select Interpreter** and select `.venv\Scripts\python.exe` for editor linting, testing, and navigation.

**Don't run `uv init` again:** this repository already has `pyproject.toml`. For a completely empty project, `uv init --bare` creates Python project metadata; it does **not** create a GitHub repository.

## 2. Start Kafka locally and confirm ingestion

Start the Kafka broker defined in `compose.yaml`:

```powershell
docker compose up -d
```

Create the topic:

```powershell
docker compose exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --create --if-not-exists --topic fleetpulse.gps.raw --partitions 3 --replication-factor 1
```

Publish 30 **synthetic**, explicitly labeled GPS events (does **not** need Geotab credentials):

```powershell
uv run python -m ingestion.synthetic_publisher --events 30 --devices 5 --rate 5
```

Read some events back from Kafka:

```powershell
docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic fleetpulse.gps.raw --from-beginning --max-messages 5
```

**Expected result:** JSON events with `source: synthetic_test` appear in the consumer. Kafka is only bound to `127.0.0.1:9092` in this local development configuration.

## 3. Obtain and inspect Geotab telemetry

1. Follow the [Geotab demo database setup](https://support.geotab.com/help/mygeotab/access-and-administration/getting-started/database-setup). Choose a Public Works fleet if available.
2. Enter your demo credentials in `.env` (never commit this file):

   ```dotenv
   GEOTAB_USERNAME=your-email@example.com
   GEOTAB_PASSWORD=your-demo-password
   GEOTAB_DATABASE=your-demo-database
   GEOTAB_SERVER=
   GEOTAB_FIRST_VERSION=0
   GEOTAB_CURSOR_PATH=state/geotab_logrecord_cursor.json
   GEOTAB_POLL_SECONDS=15
   KAFKA_BOOTSTRAP_SERVERS=localhost:9092
   KAFKA_TOPIC=fleetpulse.gps.raw
   KAFKA_API_KEY=
   KAFKA_API_SECRET=
   ```

3. Inspect your available devices and a few GPS records:

   ```powershell
   uv run python -m ingestion.inspect_geotab
   ```

4. Start incremental ingestion into the local Kafka topic:

   ```powershell
   uv run python -m ingestion.geotab_to_kafka
   ```

`GetFeed(typeName="LogRecord")` returns GPS observations and a `toVersion` token. The ingestion app uses that token on the next poll, and writes it to `state/geotab_logrecord_cursor.json` **after Kafka delivery acknowledgement**. Stop with **Ctrl+C** and restart to exercise checkpoint recovery.

**Delivery semantics:** The Geotab→Kafka boundary is **at least once**. A crash after Kafka publishing but before the cursor is saved can replay records; downstream deduplication is required. Initial polling from `GEOTAB_FIRST_VERSION=0` may retrieve substantial history. Demo timestamps can be old, even when the API is queried today.

## 4. Connect Azure Databricks to hosted Kafka

**Important:** Databricks running in Azure **cannot read Kafka on your laptop** through `localhost:9092`. For the cloud demo, use a hosted Kafka cluster reachable from Databricks (for example, Confluent Cloud). Account setup or service charges may apply.

Create the same `fleetpulse.gps.raw` topic in your hosted cluster and set these variables in your **local** `.env`:

```dotenv
KAFKA_BOOTSTRAP_SERVERS=YOUR_CLOUD_BOOTSTRAP:9092
KAFKA_API_KEY=YOUR_KAFKA_API_KEY
KAFKA_API_SECRET=YOUR_KAFKA_API_SECRET
# New destination = separate source checkpoint.
GEOTAB_CURSOR_PATH=state/geotab_cloud_cursor.json
```

The Python producer uses `SASL_SSL` when Kafka credentials are provided. Run the Geotab producer again using `uv run python -m ingestion.geotab_to_kafka`.

Create a Databricks secret scope named `fleetpulse` with secrets:

- `kafka-bootstrap`
- `kafka-api-key`
- `kafka-api-secret`

Never hardcode those values into notebooks, logs, or your GitHub repository.

### Run the Databricks pipeline in order

1. Execute `databricks/00_setup.sql` with Unity Catalog permissions to create the catalog, schemas, and checkpoint volume. If you use an existing catalog, update `CATALOG` in the notebooks and references in SQL.
2. Run `databricks/01_bronze.py` on Kafka-compatible Databricks compute. Writes `fleetpulse.bronze.gps_raw`.
3. Run `databricks/02_silver.py`. Writes `fleetpulse.silver.gps_events`.
4. Run `databricks/03_gold_state.py`. Maintains `fleetpulse.gold.device_state` using `foreachBatch` + Delta `MERGE`.

Each streaming job needs a durable, separate checkpoint location and continuous or suitably scheduled execution. These files are starter notebook scripts to deploy and run in Databricks—not standalone local `uv run` scripts. Databricks supplies the Spark runtime.

### Data layers

| Layer | Table | Responsibility |
| --- | --- | --- |
| Bronze | `fleetpulse.bronze.gps_raw` | Raw JSON + Kafka partition, offset, and timestamp |
| Silver | `fleetpulse.silver.gps_events` | Parsed, validated, event-time-stamped, deduplicated telemetry |
| Gold | `fleetpulse.gold.device_state` | One latest-known GPS record per device; guards against older arriving records |

The Gold table describes **last observed device state**, not guaranteed live connectivity or engine-on state. `is_moving` is derived from speed and is **not** equivalent to rental utilization.

## 5. Serve a Databricks AI/BI dashboard

Open `databricks/04_dashboard_queries.sql` and run each query as a separate dataset in Databricks SQL. In an AI/BI Dashboard, use:

| Visualization | Source | Question answered |
| --- | --- | --- |
| Point map / fleet table | Gold `device_state` | Where was each device last observed? |
| Moving vs. stationary counts | Gold `device_state` | Which devices appear to be moving? |
| Hourly GPS readings / average speed | Silver `gps_events` | How does fleet activity change over time? |
| Last event / received timestamps | Silver/Gold | Is telemetry fresh or delayed? |

Show the **source observation time** prominently, especially when using historical demo data. A current ingestion timestamp doesn't make an old GPS reading a current vehicle position.

## Known limitations and planned work

- The Geotab demo provides **simulated** fleet data, and the available diagnostics depend on the selected fleet/devices.
- `LogRecord` provides timestamp, position, and speed. It doesn't, by itself, prove equipment rental status, engine condition, or maintenance needs.
- Silver currently filters invalid events instead of writing a quarantine/dead-letter table.
- Silver's watermark-based deduplication is bounded; permanent deduplication/correction handling is a future design consideration.
- Future work: fault/diagnostic feeds, richer state models, schema evolution, observability, CI/CD, load testing, and a **separate MQTT IoT simulator**.
